## Requirements
### Requirement: Media storage is reusable Wevra infrastructure
The system SHALL provide a reusable media capability for catalogue-backed writable media storage that can be used by profile and other modules.

#### Scenario: Media root is configured
- **WHEN** media storage is configured
- **THEN** Wevra resolves a writable media root from Wevra-owned media configuration
- **AND** the media root is not profile-specific application configuration

#### Scenario: Multiple modules can use media
- **WHEN** more than one module needs writable media storage
- **THEN** each module uses the shared media capability
- **AND** no module creates an implicit fallback media store

### Requirement: Media keys resolve safely under the media root
The system SHALL resolve media keys or relative paths safely under the configured media root and reject unsafe paths.

#### Scenario: Valid media key resolves under root
- **WHEN** a valid media key is resolved
- **THEN** the resulting filesystem path is contained within the configured media root

#### Scenario: Unsafe media key is rejected
- **WHEN** a media key attempts path traversal or otherwise escapes the configured media root
- **THEN** media resolution fails with a clear configuration or media error

### Requirement: Media items are catalogued by ID
The system SHALL store media item catalogue records so modules can refer to media by stable media ID instead of raw filesystem paths.

#### Scenario: Media item is registered
- **WHEN** media stores or registers a file
- **THEN** the media catalogue records a stable media ID, category, storage key, content type, size, and operational timestamps
- **AND** the storage key remains safely contained under the configured media root

#### Scenario: Media stream is stored
- **WHEN** a module supplies a media stream with a category and storage key
- **THEN** media validates writable storage, writes the stream under the configured media root, counts the stored bytes, and registers the catalogue item
- **AND** the caller receives the media item ID to store in module-owned data

#### Scenario: Generated media is stored
- **WHEN** a module supplies generated bytes rather than an HTTP upload
- **THEN** it uses the same media storage contract
- **AND** it does not bypass media-owned write and catalogue behaviour

#### Scenario: Module stores media reference
- **WHEN** a module needs to remember a media file
- **THEN** the module stores the media item ID
- **AND** it does not store the raw filesystem path as its public reference

### Requirement: Media categories structure storage
The system SHALL associate each media item with a category that defines the storage namespace for the item.

#### Scenario: Profile media uses profile category
- **WHEN** profile stores a profile picture
- **THEN** media records the item with category `profile`
- **AND** the storage key is placed under the `profile/` category prefix

#### Scenario: Category storage avoids flat directories
- **WHEN** media creates a storage key for category-managed media
- **THEN** the storage key can include deterministic buckets under the category prefix
- **AND** files are not forced into one flat media root directory

### Requirement: Media resolves URLs and paths by media ID
The system SHALL resolve client-facing URLs and internal filesystem paths from media IDs through the media capability.

#### Scenario: External media serving URL is requested
- **WHEN** media is configured for externally served storage-key URLs
- **THEN** `url_for(media_id)` returns a URL based on the media item's storage key
- **AND** the URL can be served directly by an external static server such as nginx

#### Scenario: App-served media URL is requested
- **WHEN** media is configured for app-served ID URLs
- **THEN** `url_for(media_id)` returns a URL containing the media ID
- **AND** the media server resolves the ID to a storage path before sending the file

#### Scenario: Internal media path is requested
- **WHEN** application code asks for the filesystem path for a media ID
- **THEN** media resolves the ID through the catalogue
- **AND** returns the safe filesystem path for the item's storage key

### Requirement: Media storage validates writable access when needed
The system SHALL validate that media storage is usable before workflows that require writing media perform writes.

#### Scenario: Writable media workflow starts
- **WHEN** a workflow needs to store uploaded media
- **THEN** the media capability verifies the media root exists and is writable before storing files

#### Scenario: Media root is not writable
- **WHEN** a media write workflow finds the media root is missing or not writable
- **THEN** the workflow fails with a clear media configuration error

### Requirement: Media files can be served by Wevra when enabled
The system SHALL provide optional staticfiles-like serving for configured media files for local and simple deployments.

#### Scenario: App-served media is enabled
- **WHEN** media serving is enabled in configuration
- **THEN** Wevra exposes configured media files from the media root at the configured media mount path

#### Scenario: App-served media is disabled
- **WHEN** media serving is disabled in configuration
- **THEN** Wevra does not mount the media file server
- **AND** media storage remains usable for deployments that serve media externally
